# Kafka Learning Pair — Experiments (command → observation → enterprise consequence)

Two apps on one single-node KRaft broker (`order-kafka2`, `apache/kafka:4.0.0`, PLAINTEXT,
`localhost:9092`, RF 1). **This box is deliberately small** — it cannot show replication loss,
TLS/SASL/ACLs, or cluster sizing; those rows are labelled **concept-only / not demonstrated**
and live in [`enterprise/`](./enterprise/) with the property block that *would* change.

Conventions:
- `BS=localhost:9092`. Producer = `lab-producer` (`:8091`). Consumer = `lab-consumer` (`:8092`).
- Topics are all `lab-*`; consumer groups are `lab-consumer`, `lab-competitor`, `lab-txn`,
  `lab-avro-read`, and the Streams app-id group `lab-producer`. The sibling owns `order-*`.
- Every row names the concrete topic/partition/offset you should see. Where a value is
  data-dependent (a real UUID, a partition chosen by key hash) it is given as `p`/`o` with the
  rule that determines it — never a fabricated constant.

## Producer basics (B1–B10)

| # | Concept | Command / how to observe | Expected observation (topic · partition · offset) | Enterprise consequence |
|---|---------|--------------------------|----------------------------------------------------|------------------------|
| B1 | Topic + partition config (KRaft, RF 1, `lab-orders` = 3 partitions) | `curl -s localhost:8091/lab/diagnostics`; `kafka-topics.sh --bootstrap-server $BS --describe --topic lab-orders` | `lab-orders` reports **3 partitions**, each `ReplicationFactor:1`, ISR size 1; other lanes report 1 partition | Partition count is a one-way door: you cannot rebalance keys across more partitions without a new topic + migration. RF 1 here means no fault tolerance — see [X](./enterprise/X-replication-loss.md). |
| B2 | Key → deterministic partition (key = `customerId`) | `POST /lab/orders` (keyed) vs `POST /lab/orders/unkeyed`; watch the consumer lifecycle log | Same `customerId` always lands on the **same partition p** of `lab-orders`; unkeyed (null key) uses Kafka's default sticky partitioner, so consecutive small sends typically stick to one partition — even spread is NOT guaranteed, and per-customer ordering isn't guaranteed there; offset o increments per partition | Ordering is *per partition*. Keying by the business id (not a generated id) is what makes "one customer's events in order" true. Wrong key ⇒ silent loss of ordering guarantees. |
| B3 | Key, headers, payload separation (`x-lab-trace`, `x-lab-correlation`, `x-lab-schema`) | `POST /lab/orders`; read the consumer `lifecycle` log line | One line per record: `key=<customerId> headers=[x-lab-trace=…, x-lab-correlation=…, x-lab-schema=1] payload={…} decision=accept` | Route on key *before* deserializing; carry trace/correlation in headers so a consumer can correlate without parsing the body. Headers are metadata, not payload — they survive re-serialization. |
| B4 | Codec by properties (String lane vs AVRO lane) | `POST /lab/avro` then `curl -s localhost:8092/lab/avro`; inspect `_schemas` | String lanes write raw bytes; the AVRO lane writes a Confluent envelope and `_schemas` gains a new version id on schema evolution (see A-row for the two-version case) | The serializer/deserializer is chosen by a *property*, so codec changes are config, not code. Schema evolution needs a registry — without one you are stuck to inline/JSON schemas. |
| B5 | Topic creation at startup; "topic exists ⇒ bean ignored" | Start `lab-producer` twice against the same broker | First start creates `lab-*` topics (Boot `KafkaAdmin` from `NewTopic` beans); second start logs nothing new and reuses existing partitions/RF | Idempotent bootstrap lets you restart freely, but it also means a *wrong* topic created earlier is silently reused — verify topology before trusting the app. |
| B6 | Sync vs async ack (two beans + one toggle) | `POST /lab/orders` (async: `CompletableFuture`, frees the request thread) vs `POST /lab/orders/sync` (blocks a servlet thread until broker acks) | Both lanes return **202** naming topic/partition/offset — each waits for the broker ack to name real coordinates (async resolves its future on the ack; it does NOT return before confirmation). The difference is threading, not timing: async frees the request thread while waiting; sync holds a servlet thread per send | Async keeps request threads free (throughput) but you must handle the completion future; sync is simpler and blocks a thread per send — fine for low-rate, wrong for hot paths. The `DO-NOT-SHIP` class documents the blocking shape on purpose. |
| B7 | Producer flow control (`acks`, `queue.size`, `max.blocking`, linger/batch; fast producer / slow consumer) | `POST /lab/throttle {"count":N,"recordBytes":M}` with a tiny queue | When N×M exceeds the bounded buffer, the send is **refused** → HTTP **429** + `Retry-After: 1`; `/lab/pushed`/throttle ack shows accepted vs rejected counts; no OOM | A producer must be able to *say no* when it cannot absorb work. Bounded queue + short `max.block.ms` turns "grow memory until OOM" into a clean back-pressure signal the caller can act on. |
| B8 | Flush on shutdown | SIGTERM to a running `lab-producer` with in-flight async sends | Log: `lab-orders producer lane flushed during shutdown`, `raw producer lane flushed during shutdown`, then `all KafkaTemplates destroyed exactly once` | Without `flush()` on the way out, buffered-but-unacked messages are lost. Graceful shutdown must drain the send buffer before the JVM exits. |
| B9 | Don't-lose ≠ do-once (`acks=all`, idempotency key, replay window) | Push an order, kill the consumer mid-processing, restart it; check the dedup ledger | The consumer may see the record **twice** (at-least-once); the ledger keyed by `orderId` applies it once — count stays exact | Kafka gives *at-least-once* delivery; "exactly once" is a property of your *idempotent handler*, not the broker. Model idempotency keys explicitly or you will double-apply on replay. |
| B10 | Health = broker reachable | `curl -s localhost:8091/health` and `localhost:8092/lab/health` | `{brokerReachable:true, clusterId:"…"}` when the broker answers; `false` when it does not | A health check that only says "the JVM is up" hides a dead broker. Health must reflect *Kafka reachability* (cluster id / metadata), not just liveness. |

## Producer advanced + Streams/AVRO (A10–A21)

| # | Concept | Command / how to observe | Expected observation | Enterprise consequence |
|---|---------|--------------------------|----------------------|------------------------|
| A10 | Bounded retry + exponential backoff, then quarantine | `POST localhost:8092/lab/inject-failures {"percentage":30,"lane":"lab-orders"}` then push orders | Failing records are retried a bounded number of times with growing backoff, then written to `lab-rejected` (reason `handler-throw`) and **acked** — no infinite redelivery loop | An error handler needs a *budget* (max attempts + backoff) and a *quarantine* sink. Unbounded retry poisons the group; un-quarantined failures clog offsets forever. |
| A11 | Correlation / trace id end-to-end | `POST /lab/orders` returns `traceId`; read the consumer lifecycle log for that order | The `x-lab-trace` header on `lab-orders` equals the `traceId` from the push response — same value producer-out, consumer-in | Trace/correlation ids let you stitch one logical operation across many hops. Without them, debugging a cross-service flow means grepping by time. |
| A12 | Back-pressure 429 + `Retry-After` | see B7 (`/lab/throttle`) | **429** with `Retry-After: 1` when the bounded queue refuses; caller can back off and retry | The *response* must carry a machine-readable retry hint, not just an error — otherwise callers stampede on retry. |
| A13 | Push-time logging on completion (async done-branch) | `POST /lab/orders`; watch producer log after the 202 is returned | After the broker acks: `push acknowledged: orderId=… topic=lab-orders partition=p offset=o` — logged in the completion future, not before | Logging the metadata *after* the ack (in the done-branch) is what makes "partition/offset" real rather than guessed. Logging before the ack lies about where the record went. |
| A14 | Atomic multi-topic push (transaction manager, `transaction-id-prefix`) | `POST /lab/txn {"orderId":"…","left":"…","right":"…","forceRollback":true}` | On commit: one record each on `lab-ack-a` and `lab-ack-b`. With `forceRollback:true`: **neither** topic advanced (both rolled back) | Multi-topic side effects that must stand or fall together need a *transaction* + a stable `transaction-id-prefix`. Without it, a partial write leaves the system inconsistent. |
| A15 | PoS endpoints + metrics + audit trail | `GET /lab/pushed`, `/lab/diagnostics`, `/lab/metrics` (producer) | `/lab/pushed` lists every acked push with topic/partition/offset; `/lab/diagnostics` shows per-partition next-offsets; metrics expose listener/producer counters | Observability is a first-class surface: an audit trail of *what was pushed where* and live offsets/metrics let you answer "where is my data?" without a debugger. |
| A16 | Profiles dev vs prod (TLS/SASL/multi-host block) | compare `application.properties` vs `application-prod.properties` | Dev uses PLAINTEXT single host; the prod file carries a **commented** TLS/SASL/ACL + multi-broker block naming what this box cannot show | The prod property block documents the *delta* you must apply for a real deployment (security, multiple brokers, real RF) without pretending the dev box has it. See [X](./enterprise/X-security-tls-sasl-acl.md). |
| A17 | Kafka Streams: stateless + **stateful** per-customer running total | `POST /lab/pending {"customerId":"c-1","amount":10}` a few times; `GET /lab/accepted` | Each push to `lab-pending` (key = `customerId`) flows through the app-id group `lab-producer` and emits a running total per customer to `lab-accepted`; `/lab/accepted` returns totals **in push order**, each with its real partition/offset | Streams gives you stateful, exactly-once-ish aggregation *inside* the broker topology. The state store changelog (`lab-producer-lab-running-totals-changelog`) is where the running state lives — it is a topic too. |
| A18 | Metrics: Boot metrics + Micrometer (+ listener labels) | `GET localhost:8092/lab/metrics` | `spring.kafka.listener.*` meters carry a `lab.lane=orders` tag (applied via a `MeterFilter`, because spring-kafka 4.x's observation-convention hook is not reachable in this build) | Per-listener labels are what let you tell *which* consumer group/lanes are lagging or erroring in one dashboard. Untagged listener metrics blur distinct lanes together. |
| A19 | Hot reload while messages flow (Boot DevTools) | — **not demonstrated** — | **DEGRADED:** `spring-boot-devtools` is not on the classpath (JDK 25 / Boot 4.1.2 build); the fallback is *restart without drain*. Recorded here rather than faked. | Hot reload changes behaviour mid-flow on a dev box, but in prod you deploy releases. The lesson (config/behaviour can change under load) is real; the DevTools mechanism is dev-only and is labelled as such. |
| A20 | Broker-owned state read-only (`__consumer_offsets`, `_schemas`) | `GET /lab/diagnostics` (both apps) | Diagnostics report `hasConsumerOffsetsTopic:true` and `hasSchemasTopic:true`; **no** app write path touches either topic | Offset commits and registered schemas are *broker-owned* state. Applications read them for diagnostics but must never write to them directly — that is the broker's job. |
| A21 | Diagnostics & tuning (JVM/OS + Boot metadata; where backlog shows in memory) | `GET /lab/backlog`, `/lab/diagnostics`; JVM heap view of the listener queue | `/lab/backlog` reports the in-flight queue size and per-partition lag (`next offset − committed offset`); a slow handler grows the in-process queue before it grows broker lag | Backlog lives in two places: **broker-side** (offset gap, durable) and **in-process** (consumer queue, volatile). Tuning means knowing which one you are looking at — a full broker with an empty in-process queue is a different problem than the reverse. |

## Consumer lanes (C1–C9 + consumer advanced A10b–A16b)

| # | Concept | Command / how to observe | Expected observation | Enterprise consequence |
|---|---------|--------------------------|----------------------|------------------------|
| C1 | Pop non-stop, forever | Keep `lab-consumer` running after its backlog drains | The JVM stays up; a cold start processes the backlog from `earliest`; new inflow keeps being consumed | A consumer is a long-lived worker, not a job. It must survive an empty topic and pick up whatever arrives later without being restarted. |
| C2 | Backlog: cold start vs inflow-while-slow | `GET /lab/backlog` with (a) a drained queue and (b) a slow handler + fast producer | (a) in-flight 0, lag 0; (b) in-flight queue grows and/or per-partition lag (`next − committed`) rises while the handler is slow | You must distinguish *broker backlog* (durable offset gap) from *in-process queue depth* (volatile). Both matter for capacity planning. |
| C3 | Ack dial: immediate / after-processed / batch checkpoint | set `lab.ack.strategy` to each of `immediate`, `after-processed`, `batch`; push records; read offsets | `immediate`: offset commits **before** processing (loss window = one in-flight record); `after-processed`: commits after handling; `batch`: checkpoints every N records | The ack point *is* your loss window. Committing early risks lost work on crash; committing late risks redelivery. Batch trades latency for fewer commits. Each mode's window is stated explicitly, never assumed. |
| C4 | Sync vs async ack on the pull side | toggle property; watch offset-commit timing in the log | The commit timestamp moves relative to processing depending on the strategy (see C3) | Same trade-off as the push side, mirrored: when you commit relative to work determines your durability/latency balance. |
| C5 | Two listeners, one topic, one group | `POST /lab/orders` to `lab-rebalance`-style lane; groups `lab-consumer` + `lab-competitor` on the same topic | Total processing count across both listeners **equals** the message count (offsets are shared per group, so no record is processed twice) | Consumers in one group *share* work (scale-out); consumers in different groups each get a full copy. Group membership is the unit of partitioning, not the listener count. |
| C6 | Filter bean by header ⇒ filtered-out **is** acked | produce a record with `x-lab-skip=true`; watch offsets | The record is discarded *before* deserialization and its offset **advances** (it is not re-read); the filter decision is logged | A deliberate skip (e.g. "not for me") must commit so it isn't replayed forever — that is different from a failure, which should retry/quarantine. Conflating the two causes either lost skips or infinite replays. |
| C7 | Offset/partition truth | `GET /lab/diagnostics` | Per partition: the group's committed offset **and** the next (end) offset — the gap is the true backlog | "How far behind am I?" has one authoritative answer: end-offset − committed-offset, per partition. Guessing from logs is not a substitute for reading the broker. |
| C8 | Per-message lifecycle log | push one order; read the consumer log | One line per message: `topic · partition p · offset o · key · headers · payload · decision` (accept / skip-duplicate / reject-quarantine / retry) | A per-message audit line with an explicit *decision* is what makes at-least-once debugging tractable — you can see exactly why each record was handled the way it was. |
| C9 | PoS endpoints, metrics, health | `GET /lab/diagnostics`, `/lab/backlog`, `/lab/rejected`, `/lab/metrics`, `/lab/health` (consumer) | Diagnostics + backlog expose offsets/lag; `/lab/rejected` shows quarantined records with raw payload + reason + `partition@offset`; metrics show listener counters; health reflects broker reachability | The consumer's observability surface mirrors the producer's: you can answer "what did I reject and why?" and "how far behind am I?" without logs. |
| A10b | `AfterRollbackProcessor` both modes | set `lab.rollback.mode` to `retry-next-poll` vs `discard`; force a transactional failure | `retry-next-poll`: the offset is left for a later poll (reprocessed); `discard`: the record is skipped and the group offset advances past it | On rollback you must *decide* what happens to the offset. Leaving it reprocesses (safe, may loop if not idempotent); discarding skips it (fast, may lose work). The processor makes that choice explicit. |
| A12b | Transactional pop (KafkaTransactionManager + `ChainedKafkaTransactionManager` @Primary) | force a failure in the txn lane on `lab-orders` with side effects to `lab-ack-a`/`lab-ack-b` | On failure: the **source** offset on `lab-orders` is unchanged and neither ack topic advanced — the whole unit rolled back | Consuming *and* producing side effects atomically needs a transaction manager (chained where multiple producers are involved). Without it, a crash mid-side-effect leaves partial writes. |
| A13b | Graceful shutdown on the pull side | SIGTERM to `lab-consumer` with in-flight work | Log: `shutdown: pending=… applied-orders=… (un-ACKed messages stay at their offsets for the next start)`; exit 0; acked segment is **not** re-processed on restart | A clean stop commits only what was fully processed, so a restart resumes exactly where it left off — no redelivery of already-applied work. |
| A14b | Rebalance + seek (`ConsumerAwareRebalanceListener`), `GROUP_INITIAL_REBALANCE_DELAY_MS=0` | `POST /lab/listeners/competitor/off` (stop one listener of the shared group) | The survivor re-reads from the group offsets and processes whatever the stopped listener had not acked; on this single broker it is in-process only (a multi-broker cluster would also re-fetch the assignment from the controller) | Rebalance moves partitions between consumers of a group. `GROUP_INITIAL_REBALANCE_DELAY_MS=0` removes the default 3s pause so the lab's rebalance is observable immediately; in prod you usually keep the delay to reduce churn. |
| A15b | Quarantine lane ≠ filter | inject failures / send an undecodable record; `GET /lab/rejected` | The failed/undecodable record lands on `lab-rejected` with its **raw payload + reason** (e.g. `json-decode`, `handler-throw`) and the source `partition@offset`; it is then acked so it isn't replayed forever | Quarantine is a *failure* path (retry then park + reason), distinct from a *filter* (deliberate skip). Parking raw bytes + reason is what lets you later diagnose and re-drive the poisoned message. |
| A16b | Idempotent processing under crash/retry | push an order, force redelivery of the same `orderId`, restart | The dedup ledger keyed by `orderId` applies each order **exactly once**; the applied count is exact after restart despite at-least-once delivery | This is the concrete "do-not-do-twice" mechanism: a durable idempotency key checked before applying. It is what turns Kafka's at-least-once into application-level exactly-once effect. |
